Module 3: Relational Database Design

1. Informal Design Guidelines[cite: 10]

  • Semantics: Each tuple should represent one entity or relationship instance. Keep attributes of different entities separate.
  • Redundancy & Anomalies:
    • Insertion Anomaly: Cannot insert a project unless an employee is assigned to it.
    • Deletion Anomaly: Deleting the last employee on a project deletes the project itself.
    • Update Anomaly: Changing a project name requires updating 100 employee tuples.
  • Null Values: Minimize them. If an attribute is frequently null, place it in a separate relation with the primary key.
  • Spurious Tuples: Design relations to satisfy the lossless join condition. Never generate fake records when performing natural joins.

2. Functional Dependencies (FDs)[cite: 10, 11]

Definition: X → Y means if two tuples have the same value for X, they must have the same value for Y. X functionally determines Y.

Armstrong's Inference Rules (Sound & Complete)[cite: 11]

IR1 (Reflexive): If Y ⊆ X, then X → Y
IR2 (Augmentation): If X → Y, then XZ → YZ
IR3 (Transitive): If X → Y and Y → Z, then X → Z

Additional Rules:
Decomposition: If X → YZ, then X → Y and X → Z
Union: If X → Y and X → Z, then X → YZ
Pseudotransitivity: If X → Y and WY → Z, then WX → Z

Algorithm 15.1: Attribute Closure (X⁺)[cite: 11]

Input: Set of FDs F, subset of attributes X
Initialize: X⁺ := X
Repeat:
    oldX⁺ := X⁺
    For each Y → Z in F:
        If X⁺ ⊇ Y then X⁺ := X⁺ ∪ Z
Until (X⁺ == oldX⁺)

* If X⁺ contains all attributes in the relation, X is a Superkey.

Algorithm 15.2: Minimal Cover[cite: 11]

A set of FDs is minimal if: 1) Every RHS has a single attribute. 2) No FD can be removed without changing equivalence. 3) No attribute in LHS can be removed.

1. Decomposition: Replace X → {A,B} with X → A and X → B.
2. Remove Extraneous LHS Attributes: For X → A, if replacing X with (X-B) leaves the FD set equivalent, remove B from X.
3. Remove Redundant FDs: For each X → A, if it can be inferred from the remaining FDs, remove it.

3. Normal Forms (1NF to 5NF)[cite: 10]

  • Universal Relation
    • 1NF Atomic
      • 2NF Full FD on Key
        • 3NF No Transitive
          • BCNF LHS is Superkey
            • 4NF No MVDs
              • 5NF No JDs
Normal FormRule / Definition[cite: 10]
1NFNo composite attributes, no multi-valued attributes, no nested relations. All values must be atomic.
2NFEvery non-prime attribute is fully functionally dependent on every key of R. (No partial dependencies).
3NFFor every FD X → A, either:
a) X is a superkey, OR
b) A is a prime attribute. (No transitive dependencies).
BCNFFor every FD X → A, X must be a superkey. (Stricter than 3NF, drops condition b).
4NFFor every non-trivial Multivalued Dependency (MVD) X →→ Y, X must be a superkey.
5NF (PJNF)For every non-trivial Join Dependency (JD), every Ri is a superkey of R.

Properties of Decomposition[cite: 11]

  • Dependency Preservation: The union of projections of F on each decomposed relation is equivalent to F. (You shouldn't need to join tables to check an FD constraint).
  • Lossless (Non-additive) Join (NJB Test): Decomposition into R1 and R2 is lossless IF AND ONLY IF:
    (R1 ∩ R2) → (R1 - R2) OR (R1 ∩ R2) → (R2 - R1) is in F⁺.
    (The common attributes must be a superkey for at least one of the decomposed relations).

Module 4: Physical Database Design & Query Processing

1. File Storage & Organization[cite: 12]

  • Spanned vs Unspanned Records:
    Unspanned: Records cannot cross block boundaries. Wastes space at end of block.
    Spanned: Records can span across multiple blocks (using pointers). Good for variable-length.
  • Blocking Factor (bfr): Average number of records per block. bfr = ⌊ B / R ⌋ (where B = Block size, R = Record size).
  • Heap (Unordered) Files: Records appended to the end. Linear search takes b/2 accesses on average.
  • Sorted (Ordered) Files: Ordered by a specific field. Binary search takes ⌈ log&sub2;(b) ⌉ accesses.

2. Hashing Techniques[cite: 12]

  • Static Hashing: Fixed number of buckets. Collisions handled by open addressing or chaining (overflow files).
  • Extendible Hashing (Dynamic): Uses a directory of pointers.
    - Global Depth (d): Directory has 2d entries. Looks at first 'd' bits of hash.
    - Local Depth (d'): Attached to each bucket.
    - Split Rule: If bucket full and d' = d, double directory size (d=d+1) and split bucket (d'=d'+1). If d' < d, just split bucket and update pointers.
  • Linear Hashing (Dynamic): Allows expansion/shrinking without a directory structure.

3. Indexing Structures[cite: 13]

Type of Index Ordered Data File? Indexing Field Dense / Nondense
Primary Index Yes Primary Key Nondense (One entry per disk block)
Clustering Index Yes Non-Key Nondense (One entry per distinct value)
Secondary Index No (Or ordered by something else) Any (Key or Non-Key) Dense (One entry per record/value)

4. B-Trees and B+-Trees[cite: 13]

  • B-Tree: Search tree where every node is at least half-full. Data pointers are stored at both internal nodes and leaf nodes.
  • B+-Tree:
    - Data pointers are stored ONLY at the leaf nodes.
    - Internal nodes only store search keys to guide the search.
    - Leaf nodes are linked together (linked list) to provide extremely fast sequential access.
    - Node capacity: Max p-1 search values, p tree pointers.

5. Relational Algebra[cite: 14]

Unary Operators:
σ (SELECT): Filters rows. e.g., σSalary>30000(EMPLOYEE)
π (PROJECT): Filters columns. Eliminates duplicates. e.g., πLname, Salary(EMPLOYEE)
ρ (RENAME): Renames relation/attributes. e.g., ρS(B1,B2)(R)

Binary Set Operators (Require Type-Compatibility):
∪ (UNION): Tuples in R or S or both.
∩ (INTERSECTION): Tuples in both R and S.
− (DIFFERENCE): Tuples in R but not S.

Join Operators:
× (CARTESIAN PRODUCT): Every tuple in R paired with every tuple in S.
⋈ (THETA JOIN): R ⋈θ S = σθ(R × S)
* (NATURAL JOIN): Equijoin on attributes with the same name. Drops the duplicate column.
÷ (DIVISION): R(Z) ÷ S(X). Returns tuples in Y (where Z=X∪Y) that match with every tuple in S(X).

Aggregate Functions:
ℱ (AGGREGATE): e.g., DNO ℱ COUNT SSN, AVG Salary (EMPLOYEE)

6. Query Optimization (Heuristics)[cite: 15]

The query optimizer restructures the Query Tree using equivalence rules to execute faster.

  • Cascade of σ: σc1 AND c2(R) = σc1(σc2(R))
  • Commutativity of σ: σc1(σc2(R)) = σc2(σc1(R))
  • Commutativity of Joins: R ⋈ S = S ⋈ R
  • Distributing σ over ⋈: Push selections down the tree as early as possible to reduce intermediate result sizes.
  • Distributing π over ⋈: Push projections down to drop unused attributes early.

Module 5: Transaction Processing

1. ACID Properties[cite: 16]

  • Atomicity: Transaction performed in its entirety or not at all (managed by Recovery subsystem).
  • Consistency Preservation: Takes database from one valid state to another.
  • Isolation: Execution is not interfered with by other concurrent transactions (managed by Concurrency Control).
  • Durability: Once committed, changes must persist, even if system crashes.

2. Concurrency Anomalies[cite: 16]

AnomalyDescription
Lost Update (W-W)T1 reads X. T2 reads X. T1 writes X. T2 writes X. T1's write is overwritten and lost.
Dirty Read / Temporary Update (W-R)T1 writes X. T2 reads X. T1 aborts/rolls back. T2 now has an invalid "dirty" value.
Incorrect SummaryT3 is summing up values while T1 is actively moving amounts between them.
Unrepeatable Read (R-W)T1 reads X. T2 writes X. T1 reads X again and gets a completely different value.

3. Schedules and Recoverability[cite: 16]

  • All Schedules
    • Recoverable
      Commit order matters
      • Cascadeless
        No dirty reads
        • Strict
          No uncommitted R/W
  • Recoverable: If T2 reads data written by T1, T1 MUST commit before T2 commits.
  • Cascadeless: Avoids cascading rollbacks. A transaction only reads items that are already committed.
  • Strict: A transaction can neither read NOR write an item X until the last transaction that wrote X has committed/aborted.

4. Serializability[cite: 16]

A schedule is Serializable if it is equivalent to some serial execution of the same transactions.

  • Conflict Equivalence: Two schedules are conflict equivalent if the relative order of any two conflicting operations is the same in both.
  • Conflicting Operations: Two operations conflict if they belong to different transactions, access the same data item, and at least one is a Write.
    (Read-Write, Write-Read, Write-Write).

PYQ Cheat Codes: Master Algorithms

Follow these mechanical steps verbatim to secure full marks on the heavily tested 10-mark questions.

Code 1: BCNF Decomposition

Problem: "Check if relation is in BCNF. If not, decompose."

Step 1: Find Candidate Keys
- List all attributes not on the RHS of any FD.
- Find their closure. If they determine all attributes, they are the key.

Step 2: Check BCNF Condition
- For EVERY given FD (X → Y), check if LHS (X) is a Candidate Key (or Superkey).
- If ANY FD has an LHS that is NOT a key → The relation is NOT in BCNF.

Step 3: Decompose
- Let the violating FD be X → Y.
- Split relation R into:
   R1(X ∪ Y)   // The violating FD attributes
   R2(R - Y)      // Original attributes MINUS the RHS of violating FD
- Check if R1 and R2 are in BCNF. If not, repeat.

Code 2: B+ Tree Insertion Logic

Problem: "Construct a B+ tree of order p=4 with values..."

Node Constraints for p=4:
- Max pointers = 4. Max keys = 3.
- Min pointers = 2 (for internal nodes).

Insertion Rules:
- ALWAYS insert into a leaf node keeping it sorted.
- If leaf overflows (has 4 keys): SPLIT.
- B+ Tree Split Rule: Split into Left and Right.
   - Left gets first ⌈n/2⌉ keys.
   - Right gets the rest.
   - COPY the first key of the Right node UP to the parent. (Unlike B-trees where it is moved, in B+ trees it stays in the leaf for data access).
- Keep linking leaf nodes horizontally!

Code 3: Heuristic Query Optimization

Problem: "Construct Initial Query Tree and Optimized Query Tree using heuristics."

Initial Tree:
1. Put all tables at the bottom, joined by Cartesian Products (X).
2. Put ONE giant SELECT (σ) node above them containing ALL WHERE conditions.
3. Put ONE PROJECT (π) node at the very top with the SELECT columns.

Optimization Steps:
1. Deconstruct σ: Break the giant σ into individual σ nodes.
2. Push σ down: Move σ conditions down the tree to sit directly above the base tables they filter. (e.g., σ Dept='CSE' goes right above Department table).
3. Convert × to ⋈: Replace Cartesian Products that have a join condition immediately above them into a Theta-Join (⋈) node.
4. Push π down: Add Projection nodes right above tables to filter out unused columns early. (Keep primary/foreign keys needed for joins higher up).

Code 4: Conflict Serializability (Precedence Graph)

Problem: "Check if schedule S is conflict serializable."[cite: 16]

Algorithm 20.1:
1. Draw a circle (node) for each transaction (T1, T2, T3).
2. Scan the schedule left-to-right. Look for operations on the same item by different transactions where at least one is a WRITE.
3. Draw directed edges for conflicts:
   - Read-Write: If T1 reads X, then T2 writes X → Draw T1 → T2
   - Write-Read: If T1 writes X, then T2 reads X → Draw T1 → T2
   - Write-Write: If T1 writes X, then T2 writes X → Draw T1 → T2
4. The Verdict:
   - If the graph contains a CYCLE (e.g., T1→T2→T1) → NOT Conflict Serializable.
   - If NO cycle → Conflict Serializable.
5. Equivalent Serial Schedule: Perform a topological sort (node with 0 incoming edges goes first).
