Module 3: Relational Database Design

Database design is the mathematical process of removing redundancy. We use Functional Dependencies (FDs) to determine how attributes relate, and Normal Forms to split tables systematically without losing information[cite: 10, 11].

Boyce-Codd Normal Form (BCNF)

A relation is in BCNF if and only if for every non-trivial functional dependency X → Y, the left-hand side (X) is a Superkey[cite: 10].

The Golden Rule: Every arrow must start from a key. If an attribute that is NOT a key uniquely identifies another attribute, your table is broken and must be decomposed.

How to decompose a BCNF Violation: If X → Y violates BCNF in relation R:
1. Create R1(X ∪ Y) — The table for the violating FD. The key is X.
2. Create R2(R - Y) — The original table minus the right-hand side of the violating FD.

Step 2: Check BCNF Violation
AB → C
Does the first violate BCNF, i.e. is AB a key for R? The answer is yes, so no violation.[cite: 19]
B → D
Does this violate BCNF? Yes, because B is not a key. So we create 2 relations: R1(BD) and R2(ABC).[cite: 19]

Step 3: Decompose
For (BD) the candidate key is B. The only FD that applies here is B → D so it is in BCNF.[cite: 19]
For (ABC), the candidate keys are AB and BC. The first FD applies, AB → C and AB is a key so it is in BCNF. The second FD doesn't apply (there is no D in it), and the third FD does apply (C → A). Is C a key no, so we need to decompose by creating a new relation schema made up of the FD, and pulling out the right side of the FD from the original.[cite: 19]
Final state: (BD)(CA)(BC)
BD is still in BCNF as before.[cite: 19]
CA has C as the candidate key, and the only FD that applies is C → A. It is in BCNF. BC has BC as the candidate key, and no FDs apply, so it is in BCNF.[cite: 19]
Our final decomposition is: (BD)(CA)(BC).[cite: 19]

Step 4: Dependency Preservation
This BCNF decomposition did not preserve dependencies. We have lost the ability to check AB → C without doing a join. In this case a 3NF decomposition would be better served, which was back at: (BD)(ABC).[cite: 19]

Q5. Let R=(B,C,D,E,F,G) be a relation schema with dependencies: D → G, F → B, FD → E, B → C. Find all possible super keys and minimal super keys. Find implied FDs applying axiom rules.[cite: 25]
AI-Generated Solution Fall Inter Sem 2023-2024
Step 1: Find Minimal Super Keys (Candidate Keys)
Identify attributes that never appear on the right side of any FD: F and D.
Calculate closure of (FD)+:
- From D → G: {F, D, G}
- From F → B: {F, D, G, B}
- From B → C: {F, D, G, B, C}
- From FD → E: {F, D, G, B, C, E}
Since (FD)+ contains all attributes of R, and neither F nor D alone can determine all attributes, FD is the sole minimal super key (Candidate Key).

Step 2: Find Possible Super Keys
A super key is any combination of attributes that contains the minimal super key. Since FD is the minimal key, any set containing {F, D} is a super key. Examples: {F,D}, {F,D,A}, {F,D,B}, {F,D,B,C}, etc. (Total of 24 = 16 super keys since 4 attributes are remaining).

Step 3: Implied FDs using Axioms
1. Transitivity Rule: If F → B and B → C, then F → C.
2. Augmentation Rule: If D → G, then adding F to both sides gives FD → FG.
3. Union Rule: Since F → B and F → C (from step 1), then F → BC.
4. Decomposition: Since FD → E, we know FD uniquely identifies E.

Multivalued Dependencies (4NF)

A Multivalued Dependency (MVD) X →→ Y means that for a single value of X, there is a set of values for Y, and this set is completely independent of any other attribute Z in the table[cite: 10].

If a student is enrolled in 3 subjects and participates in 2 sports, putting this in one table creates 3 × 2 = 6 duplicate rows. 4NF Rule: A relation is in 4NF if it contains no non-trivial MVDs where X is not a superkey[cite: 11]. To fix it, split the independent multi-valued attributes into their own tables.

Module 4: Physical Database Design & Query Processing

This module transitions from logical design to how data physically sits on hard disks, how we build indexes to find it, and how we optimize the mathematical queries used to retrieve it[cite: 12, 13, 14, 15].

File Organization & Storage Mathematics

Data on disks is divided into Blocks (size B). Database Records (size R) are packed into these blocks[cite: 12].

  • Blocking Factor (bfr): The number of whole records that fit into one block.
    Formula: bfr = ⌊ B / R ⌋ records/block. (We round down because we assume unspanned records, meaning a record cannot be split across two blocks)[cite: 12].
  • Blocks Required (b): Total blocks to hold a file of r records.
    Formula: b = ⌈ r / bfr ⌉ blocks. (We round up because remaining records need a partial block).
  • Binary Search Cost: If the file is sorted, the maximum block accesses to find a record is ⌈ log2(b) ⌉[cite: 12].

Dynamic & Extendible Hashing

Static hashing creates permanent bucket overflows. Extendible Hashing dynamically doubles a directory of pointers based on the binary hash of the search keys[cite: 12].

  • Global Depth (GD): The number of bits the directory uses. Directory size = 2GD.
  • Local Depth (LD): The number of bits a specific bucket uses.
  • If a bucket overflows and LD = GD: Double directory (GD+1), split bucket (LD+1).
  • If a bucket overflows and LD < GD: Just split the bucket (LD+1) and adjust pointers.

Dynamic Multilevel Indexing: B+ Trees

A B+ tree is the industry standard for database indexing. It differs from a standard B-tree in one critical way: Data pointers are stored ONLY at the leaf nodes[cite: 13]. Internal nodes only contain search keys to guide the traversal. Leaf nodes are linked together to allow fast sequential scanning[cite: 13].

For a B+ tree of order p:

  • Internal nodes have maximum p pointers and p-1 search keys[cite: 13].
  • When a node overflows (reaches p keys), it SPLITS.
  • B+ Tree Split Rule: The middle key is sent UP to the parent. However, because all data must reside at the leaf level, if a leaf node splits, the middle key is copied up, but also remains in the right-half leaf node.

Heuristic Query Optimization (Query Trees)

A Query Tree represents the mathematical order of operations for a query. The Optimizer uses heuristic rules to transform the tree to run faster[cite: 15]. The primary rule is: Filter as early as possible. By pushing Selection (σ) and Projection (Π) operations down the tree toward the base tables, we drastically reduce the size of intermediate tables generated by Joins[cite: 15].

Module 5: Transaction Processing and Recovery

A transaction is a logical unit of work (e.g., transferring money). Because databases handle thousands of users concurrently, operations interleave. We must ensure these interleaved schedules don't destroy data integrity[cite: 16].

ACID Properties & Types of Anomalies

  • Atomicity: Transaction is performed in its entirety or not at all (managed by Recovery subsystem)[cite: 16].
  • Consistency: Database transitions from one valid state to another[cite: 16].
  • Isolation: Transactions executing concurrently do not interfere with each other (managed by Concurrency Control)[cite: 16].
  • Durability: Once committed, changes are permanent and survive crashes[cite: 16].

Concurrency Anomalies:

  • Lost Update: T1 reads X, T2 reads X, T1 writes X, T2 writes X. T1's update is overwritten and lost[cite: 16].
  • Dirty Read (Temporary Update): T1 modifies X. T2 reads X. T1 crashes and rolls back. T2 now has "dirty" data that technically never existed[cite: 16].

Conflict Serializability

A concurrent schedule is "safe" if its operations can be rearranged into a strict serial schedule (T1 completes, then T2 completes) without changing the outcome. We call this Conflict Serializable[cite: 16].

Two operations conflict if they are from different transactions, access the same data item, and at least one is a Write (i.e., R-W, W-R, W-W)[cite: 16].

The Precedence Graph Algorithm:

  1. Create a node for each transaction.
  2. For every conflict between TA and TB, draw a directed edge from TA → TB if TA's operation occurs first in time[cite: 16].
  3. If the graph has a CYCLE, the schedule is NOT serializable[cite: 16].

Q23. Determine whether the below schedule S2 is strict, cascadeless, recoverable, or nonrecoverable and justify your answer.[cite: 24]
S2: r1(A); r2(C); r3(A); r1(C); r2(B); r3(B); w1(A); c1; w2(C); w3(B); w2(B); c3; c2;
AI-Generated Solution Fall 2025-2026
1. Recoverable / Cascadeless Analysis
A schedule is Cascadeless if no transaction reads data written by an uncommitted transaction. Let's trace the reads:
- r1(A), r2(C), r3(A), r1(C), r2(B), r3(B): All these reads occur before any transaction performs a write operation. Therefore, they all read the initial committed values from the database.
Since no transaction reads uncommitted data, S2 is Cascadeless.
Because every cascadeless schedule is strictly recoverable, S2 is Recoverable.

2. Strict Analysis
A schedule is Strict if a transaction can neither read nor write an item X until the last transaction that wrote X has committed or aborted.
Let's trace the writes:
- w1(A): Overwrites initial A. (Strict). c1 commits T1.
- w2(C): Overwrites initial C. (Strict).
- w3(B): Overwrites initial B. (Strict).
- w2(B): T2 overwrites the value of B written by T3. However, T3 has NOT committed yet (c3 happens after w2(B)).
Because T2 writes to B before T3 commits, S2 is NOT Strict.

Final Verdict: S2 is Cascadeless and Recoverable, but it is NOT Strict.
