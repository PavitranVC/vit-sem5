Module 3: Relational Database Design

Database design is the mathematical process of removing redundancy. We use Functional Dependencies (FDs) to determine how attributes relate, and Normal Forms to split tables systematically without losing information[cite: 10, 11].

Understanding Boyce-Codd Normal Form (BCNF)

A relation is in BCNF if and only if for every non-trivial functional dependency X → Y, the left-hand side (X) is a Superkey[cite: 10].

The Golden Rule: Every arrow must start from a key. If an attribute that is NOT a key uniquely identifies another attribute, your table is broken and must be decomposed.

How to decompose a BCNF Violation: If X → Y violates BCNF in relation R:
1. Create R1(X ∪ Y) — The table for the violating FD. The key is X.
2. Create R2(R - Y) — The original table minus the right-hand side of the violating FD.

PYQ: BCNF Check & Decomposition

Fall 2024-2025
Consider the relation R = (A,B,C,D) and set of functional dependencies F = {AB → C, B → D, C → A}[cite: 3].
(i) What are the candidate keys?
(ii) Is the relation in BCNF? If not, decompose into BCNF.
(iii) Is the decomposed relation dependency preserving?

Step-by-Step Solution:

  1. Calculate Attribute Closures to find Candidate Keys.

    We need to find which combinations of attributes can determine all attributes {A,B,C,D}. Look at the FDs: B is never on the right side of an arrow, so B must be part of any candidate key.

    • Start with B: B+ = {B, D} (Using B → D). This is not all attributes.
    • Try AB: (AB)+ = {A, B, C, D} (Using AB → C gives {A,B,C}, then B → D gives {A,B,C,D}). AB is a Candidate Key[cite: 3].
    • Try BC: (BC)+ = {B, C, A, D} (Using C → A gives {A,B,C}, then B → D gives {A,B,C,D}). BC is a Candidate Key[cite: 3].
  2. Check BCNF Conditions for each FD.

    For BCNF, the left side of every FD must be a Candidate Key or Superkey.

    • AB → C: Is AB a key? Yes. (Passes BCNF).
    • B → D: Is B a key? No. (Violates BCNF)[cite: 3].
    • C → A: Is C a key? No. (Violates BCNF)[cite: 3].

    Because there are violations, R is NOT in BCNF.

  3. Decompose the Relation.

    Let's use the violating FD B → D to decompose R(A,B,C,D).

    • R1(B, D) — Formed from the FD itself. Key is B. In BCNF[cite: 3].
    • R2(A, B, C) — Formed by (R - D). We must check if R2 is in BCNF.

    Check R2(A, B, C) against remaining FDs (AB → C, C → A):

    • C → A violates BCNF in R2 because C is not a key of R2 (C+ = {A,C}).
    • Decompose R2 using C → A:
    • R2a(C, A) — Key is C. In BCNF[cite: 3].
    • R2b(B, C) — (R2 - A). Key is BC. In BCNF[cite: 3].

    Final Decomposition: (B,D), (C,A), (B,C)[cite: 3].

  4. Check Dependency Preservation.

    We originally had AB → C. In our final tables, A, B, and C are never in the same table together. Therefore, we have lost the ability to check AB → C without performing a join. This decomposition is NOT dependency preserving[cite: 3].

Understanding Multivalued Dependencies (4NF)

A Multivalued Dependency (MVD) X →→ Y means that for a single value of X, there is a set of values for Y, and this set is completely independent of any other attribute Z in the table[cite: 10].

If a student is enrolled in 3 subjects and participates in 2 sports, putting this in one table creates 3 × 2 = 6 duplicate rows. 4NF Rule: A relation is in 4NF if it contains no non-trivial MVDs where X is not a superkey[cite: 11]. To fix it, split the independent multi-valued attributes into their own tables.

PYQ: 4NF Normalization

Fall 2023-2024
Consider a Student table which has information about the subjects and the activity the students have enrolled in. Subject and Activity are two attributes that are independent of each other. Check whether the given table is in 4NF? If not, partition the table and convert to 4NF[cite: 1].

Step-by-Step Solution:

  1. Identify the MVDs:

    Because a Student has multiple Subjects, and multiple Activities, and they are independent, the table exhibits the following MVDs[cite: 1]:

    Student →→ Subject
    Student →→ Activity

    Because `Student` is not a unique primary key (due to the multiple rows per student), this violates 4NF.

  2. Decompose into 4NF:

    We separate the independent multi-valued attributes into two relations, both linked by the determining attribute (`Student`)[cite: 1].

    • R1(Student, Subject) — Key: {Student, Subject}
    • R2(Student, Activity) — Key: {Student, Activity}

    This removes the Cartesian product of duplicates and satisfies 4NF[cite: 1].

Module 4: Physical Database Design & Query Processing

This module transitions from logical design to how data physically sits on hard disks, how we build indexes to find it, and how we optimize the mathematical queries used to retrieve it[cite: 12, 13, 14, 15].

File Organization & Storage Mathematics

Data on disks is divided into Blocks (size B). Database Records (size R) are packed into these blocks[cite: 12].

  • Blocking Factor (bfr): The number of whole records that fit into one block.
    Formula: bfr = ⌊ B / R ⌋ records/block. (We round down because we assume unspanned records, meaning a record cannot be split across two blocks)[cite: 12].
  • Blocks Required (b): Total blocks to hold a file of r records.
    Formula: b = ⌈ r / bfr ⌉ blocks. (We round up because remaining records need a partial block).
  • Binary Search Cost: If the file is sorted, the maximum block accesses to find a record is ⌈ log2(b) ⌉[cite: 12].

PYQ: Disk Block & Search Calculations

Fall 2023-2024
Consider an ordered file with 50,000 records stored on a disk with block size B=512 bytes. File records are of fixed size and are un-spanned, with record length R=50 bytes[cite: 1].
(a) How many blocks are needed for the file?
(b) How many blocks access is needed if a binary search is performed?

Step-by-Step Solution:

  1. Calculate Blocking Factor (bfr):

    We divide block size by record size: bfr = ⌊ 512 / 50 ⌋ = ⌊ 10.24 ⌋ = 10 records/block[cite: 1].

  2. Calculate Total Blocks (b):

    Divide total records by blocking factor: b = ⌈ 50000 / 10 ⌉ = 5000 blocks[cite: 1].

  3. Calculate Binary Search Cost:

    Binary search formula: ⌈ log2(b) ⌉ = ⌈ log2(5000) ⌉[cite: 1].

    Since 212 = 4096 and 213 = 8192, it takes 13 block accesses[cite: 1].

Dynamic Multilevel Indexing: B+ Trees

A B+ tree is the industry standard for database indexing. It differs from a standard B-tree in one critical way: Data pointers are stored ONLY at the leaf nodes[cite: 13]. Internal nodes only contain search keys to guide the traversal. Leaf nodes are linked together to allow fast sequential scanning[cite: 13].

For a B+ tree of order p:

  • Internal nodes have maximum p pointers and p-1 search keys[cite: 13].
  • When a node overflows (reaches p keys), it SPLITS.
  • B+ Tree Split Rule: The middle key is sent UP to the parent. However, because all data must reside at the leaf level, if a leaf node splits, the middle key is copied up, but also remains in the right-half leaf node.

Relational Algebra Translation

Relational algebra is the theoretical mathematical foundation of SQL. You must know the Greek symbols[cite: 14]:

σ (Sigma)SELECT: Filters rows (WHERE clause). e.g., σSalary > 5000(Emp)
Π (Pi)PROJECT: Filters columns (SELECT clause). e.g., ΠName(Emp)
⋈ (Bowtie)JOIN: Combines tables based on a condition.
ρ (Rho)RENAME: Renames a table or columns. e.g., ρE(Employee)

PYQ: Relational Algebra Translation

Fall 2023-2024
Relations: employee(emp-name, street, city), works(emp-name, company-name, salary), company(company-name, city).
Write RA for: "Find the names, street address, and cities of residence of all employees who work for Honda Company and earn more than 10,000"[cite: 1].

Step-by-Step Solution:

  1. Identify the required output columns (Projection Π): We need names, street address, and cities. These belong to the employee table.
    Πemp-name, street, city(...)[cite: 1]
  2. Identify the conditions (Selection σ): Company must be 'honda' and salary > 10000. These belong to the works table.
    σcompany-name='honda' AND salary>10000(...)[cite: 1]
  3. Join the tables: Since we need output from employee but conditions from works, we must join them on their common attribute emp-name. We can rename employee to e for simplicity.
    (ρe(employee) ⋈e.emp-name=works.emp-name works)[cite: 1]
  4. Combine into final expression:
    Πe.emp-name, e.street, e.city ( σcompany-name='honda' AND salary>10000 ( ρe(employee) ⋈e.emp-name=works.emp-name works ) )[cite: 1]

Heuristic Query Optimization (Query Trees)

A Query Tree represents the mathematical order of operations for a query. The Optimizer uses heuristic rules to transform the tree to run faster[cite: 15]. The primary rule is: Filter as early as possible. By pushing Selection (σ) and Projection (Π) operations down the tree toward the base tables, we drastically reduce the size of intermediate tables generated by Joins[cite: 15].

PYQ: Query Tree Optimization

Fall 2025-2026
Schema: EMP(ENO, ENAME), PROJ(PNO, PNAME), ASG(ENO, PNO, DUR).
Query: SELECT ENAME FROM PROJ P, ASG G, EMP E WHERE G.ENO=E.ENO AND G.PNO=P.PNO AND E.ENAME ≠ 'J. Doe' AND P.PNAME='CAD/CAM' AND (G.DUR=12 OR G.DUR=24)
Construct Initial Query Tree and Optimized Query Tree using Heuristics[cite: 4].

Step-by-Step Solution:

  1. Construct the Initial Query Tree:

    The initial canonical tree takes the dumbest possible approach: It Cartesian multiplies (×) all tables together at the bottom, applies ONE giant Selection (σ) with all the WHERE conditions above it, and does ONE Projection (Π) at the top[cite: 4].

    Π ENAME
    |
    σ G.ENO=E.ENO AND G.PNO=P.PNO AND E.ENAME ≠ 'J. Doe' ...
    |
    ×
    ×
    EMP
    ASG
    PROJ
  2. Apply Optimization Rule 1: Push Down Selections (σ)

    We break the giant σ into individual conditions and push them down to the specific tables they apply to, so we filter rows before joining[cite: 15].

    • Push σENAME ≠ 'J. Doe' down to sit right above EMP[cite: 4].
    • Push σPNAME = 'CAD/CAM' down to sit right above PROJ[cite: 4].
    • Push σDUR=12 OR DUR=24 down to sit right above ASG[cite: 4].
  3. Apply Optimization Rule 2: Convert Cartesian Products to Theta Joins (⋈)

    We combine the join conditions (G.ENO=E.ENO and G.PNO=P.PNO) with the × operators to turn them into efficient Join operations[cite: 15].

    Π ENAME
    |
    ⋈ G.ENO = E.ENO
    ⋈ G.PNO = P.PNO
    σ PNAME='CAD/CAM'
    PROJ
    σ DUR=12 OR DUR=24
    ASG
    σ ENAME ≠ 'J. Doe'
    EMP

Module 5: Transaction Processing and Recovery

A transaction is a logical unit of work (e.g., transferring money). Because databases handle thousands of users concurrently, operations interleave. We must ensure these interleaved schedules don't destroy data integrity[cite: 16].

ACID Properties & Types of Anomalies

  • Atomicity: Transaction is performed in its entirety or not at all (managed by Recovery subsystem)[cite: 16].
  • Consistency: Database transitions from one valid state to another[cite: 16].
  • Isolation: Transactions executing concurrently do not interfere with each other (managed by Concurrency Control)[cite: 16].
  • Durability: Once committed, changes are permanent and survive crashes[cite: 16].

Concurrency Anomalies:

  • Lost Update: T1 reads X, T2 reads X, T1 writes X, T2 writes X. T1's update is overwritten and lost[cite: 16].
  • Dirty Read (Temporary Update): T1 modifies X. T2 reads X. T1 crashes and rolls back. T2 now has "dirty" data that technically never existed[cite: 16].

Conflict Serializability

A concurrent schedule is "safe" if its operations can be rearranged into a strict serial schedule (T1 completes, then T2 completes) without changing the outcome. We call this Conflict Serializable[cite: 16].

Two operations conflict if they are from different transactions, access the same data item, and at least one is a Write (i.e., R-W, W-R, W-W)[cite: 16].

The Precedence Graph Algorithm:

  1. Create a node for each transaction.
  2. For every conflict between TA and TB, draw a directed edge from TA → TB if TA's operation occurs first in time[cite: 16].
  3. If the graph has a CYCLE, the schedule is NOT serializable[cite: 16].

PYQ: Precedence Graphs & Serializability

Fall 2024-2025
Check whether the given Schedule S1 is conflict serializable by constructing a precedence graph[cite: 3].
S1: r1(A); r3(B); r3(A); r2(B); r2(C); w3(B); w2(C); r1(C); w1(A); w1(C)

Step-by-Step Solution:

  1. Create Nodes:

    We have transactions T1, T2, and T3. Draw three circles[cite: 16].

  2. Scan for Conflicts (Left to Right):

    Look for conflicting pairs (R-W, W-R, W-W) on the same variable by different transactions.

    • Look at r3(A). It happens before w1(A). This is a Read-Write conflict on variable A. T3 operates before T1.
      Draw edge T3 → T1[cite: 3].
    • Look at r2(B). It happens before w3(B). This is a Read-Write conflict on variable B. T2 operates before T3.
      Draw edge T2 → T3[cite: 3].
    • Look at w2(C). It happens before r1(C) and w1(C). This is a Write-Read and Write-Write conflict on variable C. T2 operates before T1.
      Draw edge T2 → T1[cite: 3].

    (Note: r1(A) before w1(A) is NOT a conflict because they are the same transaction).

  3. Check for Cycles:

    Our graph has edges: T2 → T3, T3 → T1, and T2 → T1.

    Trace the paths: You can go from T2 to T3 to T1. You can go from T2 to T1. You CANNOT loop back around to where you started. There is no cycle[cite: 3].

  4. Conclusion & Equivalent Serial Schedule:

    Since there are no cycles, Schedule S1 IS conflict serializable[cite: 3].

    To find the equivalent serial schedule, perform a topological sort (node with 0 incoming edges goes first). T2 has no incoming edges. After T2, T3 has no incoming edges. Then T1.
    Equivalent Schedule: T2 → T3 → T1[cite: 3].
