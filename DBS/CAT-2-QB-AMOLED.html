Q2. Given a relational schema R(A,B,C,D,E) and a set of functional dependencies P and Q such that: P = {A → B, AB → C, D → AC, D → E}, Q = {A → BC, D → AE}. Check whether P and Q are equivalent?
Teacher's Solution Fall 2023-2024
Answer: [4 Marks]
To check P ⊆ Q
Let's find closure of the left side of each FD of P using FD Q.
1. A+ = ABC (using A → BC)
2. AB+ = ABC (using A → BC)
3. D+ = DAEBC (using D → AE and A → BC)
4. D+ = DAEBC (using D → AE and A → BC)
Now compare closure of each A, AB, D and D calculated using FD Q with the right-hand side of FD P. Closure of each A, AB, D and D has all the attributes which are on the right-hand side of each FD of P. Hence, we can say P is a subset of Q.

To check Q ⊆ P
Using definition of equivalence of FD set, let us determine the right-hand side of the FD set of Q using FD set P.
Given P = {A → B, AB → C, D → AC, D → E} and Q = {A → BC, D → AE}
Let us find closure of the left side of each FD of Q using FD P.
1. A+ = ABC (using A → B and AB → C)
2. D+ = DACEB (using D → AC, D → E, and A → B)
Now compare closure of each A, D calculated using FD P with the right-hand side of FD Q. Closure of each A and D has all the attributes which are on the right-hand side of each FD of Q. Q is a subset of P.
Hence P is equivalent to Q.
Q3. Consider the following relation and set of functional dependencies and answer the following: R = (ABCD), F = {AB → C, B → D; C → A}.
(i) What is/are the candidate key?
(ii) Is the given relation present in the BCNF or not? If not then decompose into BCNF.
(iii) Is that the decomposed relation preserving the functional dependencies? If no then list the functional dependencies that are not preserved and state the reason.
Teacher's Solution Fall 2024-2025
Answer: [10 Marks]
Step 1: Compute Attribute Closure
A+ = A, B+ = BD, C+ = AC, D+ = D
AB+ = ABCD, BC+ = ABCD
So our candidate keys are AB and BC.

Step 2: Check BCNF Violation
AB → C
Does the first violate BCNF, i.e. is AB a key for R? The answer is yes, so no violation.
B → D
Does this violate BCNF? Yes, because B is not a key. So we create 2 relations: R1(BD) and R2(ABC).

Step 3: Decompose
For (BD) the candidate key is B. The only FD that applies here is B → D so it is in BCNF.
For (ABC), the candidate keys are AB and BC. The first FD applies, AB → C and AB is a key so it is in BCNF. The second FD doesn't apply (there is no D in it), and the third FD does apply (C → A). Is C a key no, so we need to decompose by creating a new relation schema made up of the FD, and pulling out the right side of the FD from the original.
Final state: (BD)(CA)(BC)
BD is still in BCNF as before.
CA has C as the candidate key, and the only FD that applies is C → A. It is in BCNF. BC has BC as the candidate key, and no FDs apply, so it is in BCNF.
Our final decomposition is: (BD)(CA)(BC).

Step 4: Dependency Preservation
This BCNF decomposition did not preserve dependencies. We have lost the ability to check AB → C without doing a join. In this case a 3NF decomposition would be better served, which was back at: (BD)(ABC).

(i) Candidate Key r = {AD, BCD}.
Observe BC → A is such that BC is not a super key. Therefore R is not in BCNF and should be decomposed:
R1 = (ABC) {A → BC, BC → A} in BCNF (super key = {A, BC})
R2 = (BCDE) {BCD → E, E → C} not in BCNF (E → C and E is not a super key).

Q6. Consider a relation R(StudentID, CourseID, Hobby, Instructor, InstructorOffice, CourseDept) used in a University Academic System, where: F = {CourseID → Instructor, Instructor → InstructorOffice, CourseID → CourseDept} and MVD: StudentID →→ Hobby. Determine candidate keys, explain why it violates 4NF, and decompose step-by-step to 4NF.
AI-Generated Solution Winter 2025-2026
Step 1: Determine Candidate Keys
Looking at the FDs, CourseID determines all course-related attributes (Instructor, InstructorOffice, CourseDept). StudentID and CourseID must be paired to uniquely identify an enrollment, but since a student can have multiple hobbies independently of courses, we must include Hobby in the key.
(StudentID, CourseID, Hobby)+ = {StudentID, CourseID, Hobby, Instructor, InstructorOffice, CourseDept}.
Candidate Key: {StudentID, CourseID, Hobby}.

Step 2: Check 4NF Violation
A relation violates 4NF if it contains a non-trivial Multivalued Dependency (MVD) X →→ Y where X is NOT a superkey.
We are given the MVD: StudentID →→ Hobby.
Since StudentID alone is NOT a superkey (it cannot determine CourseID or Instructor), this MVD causes massive data redundancy (every hobby a student has is repeated for every course they take). Thus, it violates 4NF.

Step 3: Decompose to 4NF
We isolate the independent multivalued attribute into its own table, linking it by the determinant.
R1(StudentID, Hobby) — Key: {StudentID, Hobby}. In 4NF.
R2(StudentID, CourseID, Instructor, InstructorOffice, CourseDept) — This removes the MVD, making R2 in 4NF (though technically it violates BCNF and needs further normalization to fully normalize). For the 4NF requirement, the primary MVD violation is removed.
Q7. Let R=(B,C,D,E,F,G) be a relation schema with dependencies: D → G, F → B, FD → E, B → C. Find all possible super keys and minimal super keys. Find implied FDs applying axiom rules.
AI-Generated Solution Fall Inter Sem 2023-2024
Step 1: Find Minimal Super Keys (Candidate Keys)
Identify attributes that never appear on the right side of any FD: F and D.
Calculate closure of (FD)+:
- From D → G: {F, D, G}
- From F → B: {F, D, G, B}
- From B → C: {F, D, G, B, C}
- From FD → E: {F, D, G, B, C, E}
Since (FD)+ contains all attributes of R, and neither F nor D alone can determine all attributes, FD is the sole minimal super key (Candidate Key).

Step 2: Find Possible Super Keys
A super key is any combination of attributes that contains the minimal super key. Since FD is the minimal key, any set containing {F, D} is a super key. Examples: {F,D}, {F,D,A}, {F,D,B}, {F,D,B,C}, etc. (Total of 24 = 16 super keys since 4 attributes are remaining).

Step 3: Implied FDs using Axioms
1. Transitivity Rule: If F → B and B → C, then F → C.
2. Augmentation Rule: If D → G, then adding F to both sides gives FD → FG.
3. Union Rule: Since F → B and F → C (from step 1), then F → BC.
4. Decomposition: Since FD → E, we know FD uniquely identifies E.

Q13. A sequential file is ordered on EmployeeID. The file has 100,000 records, block size = 1,000 bytes, record size = 100 bytes.
I. How many records per block? How many blocks total?
II. If you insert 2,000 new employees randomly, how many block splits or reorganizations are expected?
III. Suppose a primary index is built with one index entry per block. Compute the number of index blocks required. Assume index entry size = 10 bytes for key + 4 bytes for pointer.
IV. Suggest an alternative file organization to reduce insertion cost, and justify mathematically.
Teacher's Solution Fall 2025-2026
i) Record Per block = ⌊ Block size / Record size ⌋ = ⌊ 1000 / 100 ⌋ = 10 records.
Total Blocks required = ⌈ Total records / Records Per block ⌉ = 100000 / 10 = 10,000 blocks.
Each Block can hold 10 records.

ii) Estimated block Splits/reorganizations = New records / Records per blocks = 2000 / 10 = 200 blocks.

iii) Index entry size = Key size + block pointer = 10 + 4 = 14 bytes.
Index entry Per block = ⌊ Block size / Index entry size ⌋ = ⌊ 1000 / 14 ⌋ = 71 index entries.
Number of Index Blocks = ⌈ Total Blocks / Entry Per index block ⌉ = ⌈ 10000 / 71 ⌉ = 141 index Block required.

iv) Suggestion: B+ Tree organization. Instead of strictly sequential storage, use of B+ Tree indexing on EmployeeID is better. Insertion cost is reduced because only need to split the leaf node rather than reorganize large portions of the file.
Max entries per node (fan-out) p = ⌊ Block size / (Key + ptr) ⌋ = ⌊ 1000 / 14 ⌋ = 71.
So Internal node can have up to 71 Child Pointer.
So, number of leaf nodes = ⌈ 100000 / 71 ⌉ = 1409 leaves.
The tree height = Smallest integer h with 71h-1 ≥ 1409. 711=71, 712=5041. So need two level of indexing.
So height = root + one internal level + leaves = 3.
So Average insertion cost = 2 reads + 1 write = 3.

3 → 011

7 → 111

GD increases to 2. Directory entries: 00, 01, 10, 11. LD of Bucket 1 increases to 2.

Q45. Determine whether the below schedule S2 is strict, cascadeless, recoverable, or nonrecoverable and justify your answer.
S2: r1(A); r2(C); r3(A); r1(C); r2(B); r3(B); w1(A); c1; w2(C); w3(B); w2(B); c3; c2;
AI-Generated Solution Fall 2025-2026
1. Recoverable / Cascadeless Analysis
A schedule is Cascadeless if no transaction reads data written by an uncommitted transaction. Let's trace the reads:
- r1(A), r2(C), r3(A), r1(C), r2(B), r3(B): All these reads occur before any transaction performs a write operation. Therefore, they all read the initial committed values from the database.
Since no transaction reads uncommitted data, S2 is Cascadeless.
Because every cascadeless schedule is strictly recoverable, S2 is Recoverable.

2. Strict Analysis
A schedule is Strict if a transaction can neither read nor write an item X until the last transaction that wrote X has committed or aborted.
Let's trace the writes:
- w1(A): Overwrites initial A. (Strict). c1 commits T1.
- w2(C): Overwrites initial C. (Strict).
- w3(B): Overwrites initial B. (Strict).
- w2(B): T2 overwrites the value of B written by T3. However, T3 has NOT committed yet (c3 happens after w2(B)).
Because T2 writes to B before T3 commits, S2 is NOT Strict.

Final Verdict: S2 is Cascadeless and Recoverable, but it is NOT Strict.
